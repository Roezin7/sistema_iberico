# Estado operativo NOD3 — 20 de agosto de 2026

## Resumen

NOD3 tiene tres activos relacionados, pero no deben confundirse:

| Activo | Función actual | Estado |
|---|---|---|
| BPM | Deployment operativo real para abastecimiento y distribución | En construcción y validación con cliente |
| Ibérico | Laboratorio operativo real para ventas, compras, inventario y rentabilidad | Piloto listo para fin de semana |
| NOD3 | Método, memoria, arquitectura y patrones extraíbles | En fase de descubrimiento y documentación |

## Fase actual

### Ibérico

**Fase 0: control operativo y validación de datos.**

El sistema ya puede:

- consultar e importar evidencia de Epos Now;
- mostrar ventas por producto y método de pago;
- registrar una conciliación diaria confirmada;
- manejar cuentas abiertas como excepción;
- mantener semanas con inventario de apertura y cierre;
- capturar inventario físico;
- conservar recetas versionadas;
- probar el algoritmo FIFO de forma aislada;
- ejecutar la operación principal viernes–domingo.

El modelo de lotes FIFO ya está preparado en esquema y tiene un algoritmo probado, pero todavía no está conectado a:

- captura de compras/tickets;
- creación automática de lotes;
- recetas vigentes;
- ventas importadas;
- consumo de inventario;
- costo de ventas y margen.

Por lo tanto, **el piloto de este fin de semana debe validar el flujo operativo y la calidad de los datos, no presentar todavía una rentabilidad FIFO como definitiva**.

### BPM

Sigue siendo el deployment operativo prioritario para abastecimiento. Las modificaciones logísticas y la aprobación del cliente deben permanecer separadas del trabajo de Ibérico.

### NOD3

NOD3 no debe convertirse todavía en otra aplicación grande. Su trabajo actual es extraer principios que se repiten:

1. qué información se captura;
2. quién la confirma;
3. qué evidencia se conserva;
4. qué decisión depende de ella;
5. qué proceso se repite lo suficiente para merecer software.

- 69 pruebas aprobadas.

### Bloque técnico de compras

- `POST /api/inventario/compras` registra una compra confirmada y crea un lote por línea.
- `GET /api/inventario/lotes` permite revisar existencias por lote, fecha, costo y ticket.
- Las compras repetidas por el mismo `ticket_ref` se rechazan.
- La migración conserva compras históricas y amplía las unidades a cuatro decimales.
- Todavía falta la pantalla de captura y la carga de evidencia original del ticket.

### Bloque técnico Epos → receta → FIFO

- `POST /api/inventario/consumo-epos` permite vista previa o confirmación explícita.
- Las ventas se buscan por `epos_product_id` y, como respaldo, por nombre.
- Sólo se usan recetas `validada` vigentes para la fecha de la venta.
- Una venta sin mapeo, receta o inventario suficiente queda como excepción.
- El consumo confirmado actualiza lotes, crea el libro inmutable y guarda el costo FIFO de la venta.
- La operación es idempotente: una venta ya costeada no vuelve a descontarse.
- La pantalla de revisión de excepciones ya está publicada; falta probarla con ventas Epos reales.

## Siguiente bloque técnico

### 1. Compras recibidas — completar interfaz y evidencia

Construir la captura mínima de una compra:

- proveedor;
- fecha;
- ticket o factura;
- foto/original;
- producto interno;
- cantidad comprada;
- presentación;
- precio total;
- costo por unidad base;
- revisión humana.

La compra confirmada debe crear un lote FIFO, no modificar silenciosamente el promedio del catálogo. La API ya está preparada; falta una captura sencilla desde la aplicación y persistir el original del ticket en almacenamiento seguro.

### 2. Mapeo Epos → menú → receta — completar revisión visual

Para cada producto vendido:

```text
Epos product_id/nombre
  → producto_menu
  → receta vigente
  → ingredientes
  → consumo FIFO
```

Un producto sin mapeo debe detener el cálculo de rentabilidad de esa línea y aparecer como excepción. La API ya aplica esta regla; falta exponer la cola de excepciones en la interfaz.

### 3. Consumo de ventas

Después de confirmar un día:

- seleccionar ventas importadas del día;
- multiplicar cantidad vendida por receta;
- consumir lotes por ingrediente;
- registrar cada consumo;
- generar faltantes explícitos;
- calcular costo FIFO y margen estimado.

### 4. Inventario y merma

Al cierre de domingo:

- comparar existencia teórica contra conteo físico;
- clasificar diferencias como merma, receta, rendimiento, compra faltante o error;
- congelar el snapshot;
- usarlo como apertura de la siguiente semana.

### 5. Rentabilidad

Separar siempre:

- ventas brutas;
- descuentos;
- ventas netas;
- costo FIFO de ventas;
- merma;
- sueldos;
- gastos operativos;
- comisiones;
- utilidad operativa estimada.

El cambio de efectivo no debe presentarse como utilidad.

## Criterio para avanzar

Ibérico podrá pasar de Fase 0 a Fase 1 cuando complete una semana con:

- tres cortes diarios confirmados;
- cero duplicados de importación;
- todos los productos mapeados o exceptuados;
- compras con evidencia;
- inventario de apertura y cierre;
- diferencias explicadas;
- una rentabilidad que indique claramente qué parte es real y qué parte es estimación.

## Decisiones que NOD3 debe conservar

- La evidencia precede a la automatización.
- Una importación no se convierte automáticamente en verdad contable.
- Una receta no consume inventario hasta estar vigente y mapeada.
- Un lote no se mezcla con otro por comodidad.
- Un faltante queda explícito; nunca se convierte en cero silenciosamente.
- Un patrón repetido se convierte en producto; una excepción aislada se documenta.
